# Go distribution build and deployment guide

Choose a system in GO-SYSTEM-FOLDERS.md and work inside its directory. Run `make build`, `make test`, and `make vet`; the binary is written to bin/<System>. Every command disables workspace resolution so the module can be moved to another directory by itself. The shared native-Go source is snapshotted locally in each private module, rather than imported from a central ah5-support-go runtime. This intentionally duplicates code to provide independent packaging, like the Java support distribution.

Each Dockerfile builds from that system folder alone. `make image` creates its system-specific image. `compose.yaml` is a standalone target-cloud template; it does not embed the other authorities/brokers or a whole local cloud. Run `make prepare` to create private state/cert/secret directories and UID/GID values. Provision its configuration, credentials, certificate and own state. Set ARROWHEAD_NETWORK to the desired existing cloud network; HOST_PORT can change the loopback-only published port. Then use the folder's compose definition when deploying. These templates have been configuration-checked; no live cloud is replaced by this reorganization.

ServiceRegistry retains its properties configuration and original authentication policy defaults; configure it as required by the target cloud. The other core/support runtimes use JSON and mandatory mutual TLS. LocalCloudManager retains its environment configuration and dedicated role launcher; its provisioned identity password and scrypt console hash are required by its compose template. See each system's DEPLOYMENT.md and copied compatibility documentation for runtime dependencies and the actual supported behavior.

The copied Arrowhead-style TeX documentation is under each support system's documentation/<System>/ with its original class/figures and traceability; LocalCloudManager includes its v5.2.2 catalogue. Shared historical catalogues and core security/operations/reference documentation are under root documentation/. Documentation generators are preserved in the relevant module's cmd/ tree; their Java-source inputs remain explicit external reference inputs for regeneration. Build/test/vet never invoke those generators or require Java.

Root Makefile commands use tools/run-all.py to record per-system results under verification/. tools/verify-layout.py checks module independence and that all copied source-file hashes remain unchanged at their original paths. SOURCE-MANIFEST.json records exclusions (old binaries, build output, repository metadata and active-cloud data) and import rewrites. A fresh go.work lists all 22 independent modules for editor navigation.
